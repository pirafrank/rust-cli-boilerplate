# Agent guide for `rust-cli-boilerplate`

This document describes the repository conventions and development workflow for
`rust-cli-boilerplate`, a GitHub template for binary CLI projects written in Rust. Keep this
guide synchronized with the code, `justfile`, and CI workflows.

When this template is used for a new project, rename the crate and update this file (title,
overview, and layout) to describe the real application.

## Project overview

The template provides a ready-to-use CLI skeleton: a `clap` (derive) command line with example
`greet` and `echo` subcommands, verbosity flags via `clap-verbosity-flag`, logging via
`log`/`env_logger`, error handling via `anyhow`, and a rich `--version` output (version, commit,
build date, C library and linking type) generated by `build.rs`. Around the code it ships
tooling: `justfile` recipes, Git hooks, CI/cross-build/release/coverage/license/security
workflows, `cargo-deny` and `git-cliff` configuration, issue templates, and Dependabot setup.

## Repository layout

```text
src/
├── main.rs                  # logging, command dispatch, and top-level error handling
├── cli.rs                   # clap definition (arguments, subcommands) and long version output
└── constants.rs             # build-time constants (version, commit, build date, C library)
examples/gen_man.rs          # man-page generation (reuses src/cli.rs and src/constants.rs)
build.rs                     # exposes commit hash, build date, C lib, and linking type to the crate
hooks/                       # Git hooks (pre-commit, pre-push, commit-msg)
hooks_scripts/               # helper scripts used by hooks and recipes
scripts/release/             # release tooling: build-environment records, asset finalizing, tests
.github/workflows/           # CI, cross-build, coverage, licenses, security, and release jobs
.github/actions/             # reusable composite actions
.github/ISSUE_TEMPLATE/      # issue forms and contact links
.github/rulesets/            # importable branch rulesets
matrix.jsonc                 # build matrix (OS, target, builder) shared by workflows
justfile                     # authoritative task runner
cliff.toml                   # git-cliff changelog configuration
deny.toml                    # cargo-deny license and advisory policy
```

Commented-out dependencies in `Cargo.toml` (for example `dirs`, `tempfile`, `assert_cmd`,
`mockito`) are suggestions for projects built from the template; enable them only when needed.

## Toolchain and targets

- Rust toolchain: **stable**, as set in `rust-toolchain.toml`, with `rustfmt`, `clippy`, and
  `llvm-tools-preview`.
- Edition: **2021**. `Cargo.toml` declares the MSRV in `rust-version`.
- Release targets are defined in `matrix.jsonc`: Linux (gnu and musl, x86_64 and aarch64), macOS
  (x86_64 and aarch64), and Windows (msvc x86_64/aarch64, gnu x86_64). Keep `matrix.jsonc`,
  `rust-toolchain.toml`, and the workflows consistent when adding or removing a target.
- `build.rs` and `src/constants.rs` contain platform-specific `cfg` branches (including
  Windows); verify them on all affected platforms when changing them.

## Commands

The `justfile` is authoritative. Run commands from the repository root. Common recipes:

```sh
just check                 # cargo check --all-targets
just build                 # cargo build
just test                  # cargo test -- --nocapture
just test-integration      # integration test target
just fmt                   # format source
just fmt-check             # check formatting
just lint                  # clippy on normal targets, warnings denied
just lint-all              # clippy on all targets, warnings denied
just fix / just fix-all    # auto-fix clippy warnings (normal / all targets)
just better                # format and lint all targets
just pre-commit            # fmt-check and lint-all (used by the pre-commit hook)
just pre-push              # check and test (used by the pre-push hook)
just ci                    # clean, fmt-check, lint-all, build, and test
just msrv                  # cargo +<Cargo.toml rust-version> check --all-targets --locked
just compliance            # cargo audit and cargo deny license checks
just audit                 # cargo audit
just licenses              # cargo deny check licenses
just coverage              # generate lcov coverage output
just coverage-diff         # fail if coverage of the diff vs origin/main is under 90%
just man                   # generate man pages with examples/gen_man.rs
just docs                  # generate and open Rust documentation
just docs-verify-public    # fail on missing public documentation
just docs-verify-all       # fail on missing private documentation too
just release               # cargo build --release --locked
just install-hooks         # configure hooks/ as the Git hooks directory
```

Other recipes include `install-cargo-plugins`, `warnings`, `cargo-fix`, `clean`, `clean-dl`,
`clean-all`, `bench`, `deps`, `update-deps`, `outdated-deps`, `browse-coverage`, `codecov`, `issues`,
`pre-push-tag`, `changelog`, `prepare-release`, and `make-release`. Some require optional tools
such as `cargo-deny`, `cargo-audit`, `cargo-llvm-cov`, `cargo-edit`, `git-cliff`, `diff-cover`,
or `glow`;
do not install them merely to edit documentation.

The pre-commit hook runs `just pre-commit` when Rust files are staged (formatting and Clippy on
all targets). The pre-push hook runs
`just pre-push` (or `just pre-push-tag` when pushing a tag). Run `just ci` for the full local
equivalent of the CI workflow.

## Implementation guidance

### CLI and command behavior

Define arguments and subcommands with clap derive in `src/cli.rs`; `examples/gen_man.rs` includes
that file directly, so keep it free of dependencies on other application modules (or mirror them
in the example). Replace the example `greet` and `echo` commands with real ones, and give every
argument and subcommand a doc comment, since it becomes help text. User-facing failures should
carry useful context through `anyhow::{Context, Result}` and should not expose secrets.

### Build metadata

`build.rs` emits `GIT_COMMIT_HASH`, `BUILD_DATE`, `C_LIB`, and the `static_linking` /
`dynamic_linking` cfgs consumed by `src/constants.rs` and the `--version` output. Keep the
build script robust when `.git` is unavailable (for example in source tarballs).

### Errors, logging, and documentation

Application errors use `anyhow::Result`, `?`, and `.context()`/`.with_context()`. Use `log`
macros at the appropriate level: `error` for failures, `warn` for recoverable issues, `info` for
important user-visible progress, and `debug` for diagnostics. Logging is initialized in
`src/main.rs` and its level is controlled by the verbosity flags and `RUST_LOG`.

Write code so a human can understand, review, and maintain it. This applies to generated code
too: prefer clear names and straightforward structure, and avoid opaque or needlessly compressed
output.

Keep public APIs documented. The crate enables `#![warn(missing_docs)]`; check with
`just docs-verify-public`. Follow `rustfmt.toml`: four spaces, Unix newlines, 100-column maximum,
Rust 2021 formatting, and reordered imports/modules. Group imports as standard library,
external crates, then `crate::` imports. Use snake_case for functions and modules, PascalCase
for types and traits, and SCREAMING_SNAKE_CASE for constants. Names disallowed by
`clippy.toml` include `foo`, `baz`, `pippo`, and `pluto`.

## Testing and security

Add focused unit tests beside the implementation and integration tests under `tests/` for
behavior changes. Useful commands:

```sh
cargo test
cargo test --test integration
cargo test <test_name>
cargo test -- --nocapture
```

Prefer fixtures, mocks, and `tempfile` over network access or real user directories, and
serialize tests that share process-wide state. Run `just audit` and `just licenses` when
dependencies change; `deny.toml` defines the accepted licenses and advisory policy.

## Workflow rules

- Keep changes focused and preserve the existing module structure.
- Do not commit changes; leave commits to the human maintainer. Commit messages follow
  Conventional Commits (checked by `hooks/commit-msg` and used by `git-cliff`).
- Add sensible tests for behavior changes and update documentation when behavior or workflow
  changes.
- Avoid breaking changes without maintainer discussion and explicit consent when one is truly
  required.
- Keep the template generic: do not add project-specific logic, services, or heavy dependencies.
- Inspect existing changes before editing and preserve unrelated work.
- Release assets are built, attested (provenance and SPDX SBOM), checksummed, and cosign-signed
  by `.github/workflows/release.yml`. Pin third-party actions to commit SHAs, and keep
  `scripts/release/` tests passing (`scripts/release/run_tests.sh`).
- For release work, follow the existing `justfile` recipes and GitHub release workflow; do not
  create or tag a release as part of an ordinary implementation task.
